# MG Business Web

سامانه تحت وب مدیریت کسب‌وکار MG؛ هدف محصول، ارائه نسخه وب یکپارچه و ماژولار پلتفرم MG Business است.

## اجرای نسخه فعلی در Termux یا رایانه

سرور یکپارچه Python و SQLite رابط وب و API محلی را اجرا می‌کند؛ به Node.js یا npm نیاز نیست.

```sh
pkg update -y
pkg install git python -y
git clone https://github.com/Mahdi0383/MG-Business-Web.git
cd MG-Business-Web
python server.py
```

مرورگر همان دستگاه: http://127.0.0.1:8080

برای دسترسی دستگاه‌های دیگر در همان شبکه محلی (فقط شبکه مورد اعتماد):

```sh
MG_HOST=0.0.0.0 python server.py
```

فایل پایگاه داده بیرون از پوشه عمومی سایت و در `~/.mg-business-data/mg-business.sqlite3` نگهداری می‌شود. سرور به‌صورت خودکار هنگام اجرا و سپس هر ۲۴ ساعت یک snapshot سازگار SQLite در `~/.mg-business-data/backups` می‌سازد و ۱۴ نسخه آخر را نگه می‌دارد؛ در محیط توسعه بدون کلید، snapshot خام با دسترسی محدود سیستم‌عامل ساخته می‌شود. در محیط production، پیش‌بررسی استقرار وجود کلید رمزنگاری پشتیبان را اجباری می‌کند و snapshotها با AES-256-GCM به‌صورت جریانی رمز می‌شوند؛ کلید خارج از سرور و خارج از پوشه پشتیبان نگهداری شود. اگر پشتیبان‌گیری با خطای موقت روبه‌رو شود، سرویس با فاصله‌های افزایشی از ۶۰ ثانیه تا حداکثر یک ساعت تلاش مجدد می‌کند. برای انتشار اینترنتی، این سرور را بدون HTTPS، فایروال و reverse proxy امن مستقیماً در معرض اینترنت قرار ندهید.

تنظیمات پشتیبان خودکار از طریق متغیرهای محیطی `MG_BACKUP_INTERVAL_HOURS` (۱ تا ۱۶۸ ساعت)، `MG_BACKUP_RETENTION` (۱ تا ۳۶۵ نسخه)، `MG_BACKUP_DIR` و `MG_BACKUP_ENCRYPTION_KEY` قابل تغییر است. پوشه پشتیبان باید خارج از web root باشد. وابستگی رمزنگاری را با `python -m pip install -r requirements.txt` نصب کنید (در Debian/Ubuntu می‌توانید از بسته سیستم‌عامل `python3-cryptography` نیز استفاده کنید). برای ساخت کلید تصادفی ۳۲ بایتی:

```sh
python backup_manager.py --generate-key
```

مقدار خروجی را به‌عنوان `MG_BACKUP_ENCRYPTION_KEY` در فایل محیطی امن سرویس (`/etc/mg-business/mg-business.env`) قرار دهید و دسترسی آن را محدود کنید (`sudo chown root:root /etc/mg-business/mg-business.env && sudo chmod 600 /etc/mg-business/mg-business.env`)؛ آن را در Git، فایل پشتیبان یا همان دیسک مقصد پشتیبان نگهداری نکنید. گم‌شدن کلید به معنی غیرقابل‌بازیابی شدن نسخه‌های رمزنگاری‌شده است. محیط production بدون کلید معتبر از پیش‌بررسی عبور نمی‌کند.

برای آزمون یک نسخه پشتیبان بدون تغییر پایگاه داده اصلی، دستور بررسی مستقل را اجرا کنید؛ این دستور اصالت رمزنگاری و ساختار/کلیدهای خارجی SQLite را بررسی می‌کند:

```sh
python backup_manager.py --verify ~/.mg-business-data/backups/FILE.sqlite3.enc
```

برای بازیابی snapshot، ابتدا سرور MG را متوقف کنید، همان کلید `MG_BACKUP_ENCRYPTION_KEY` را در محیط shell تنظیم کنید و سپس اجرا کنید:

```sh
python backup_manager.py --restore ~/.mg-business-data/backups/FILE.sqlite3.enc
```

ابزار نسخه‌های قدیمی بدون رمزنگاری را نیز برای سازگاری می‌پذیرد. پیش از جایگزینی، از پایگاه داده فعلی یک نسخه ایمنی دیگر می‌سازد و snapshot انتخابی را از نظر اصالت AES-GCM، یکپارچگی SQLite و کلیدهای خارجی بررسی می‌کند.

پیش از جایگزینی، ابزار به‌صورت خودکار از پایگاه داده فعلی یک نسخه ایمنی دیگر می‌سازد و snapshot انتخابی را از نظر یکپارچگی SQLite و کلیدهای خارجی بررسی می‌کند. مسیر `--db` و `--backup-dir` نیز قابل تنظیم هستند.

برای دریافت تغییرات بعدی در نشست جداگانه:

```sh
cd ~/MG-Business-Web
git pull --ff-only
```

## ماتریس دسترسی نقش‌های کاربری

- مالک: مدیریت کامل فضای کاری، کاربران، لایسنس، پشتیبان کامل و تنظیمات مدیریتی.
- مدیر: مدیریت کالا و افزودنی، انبار، تأمین‌کننده و فاکتور خرید؛ مشاهده گزارش ممیزی و کاربران؛ بدون اختیار ایجاد کاربر یا تغییر نقش.
- صندوقدار: عملیات روزمره فروش، ثبت تراکنش مجاز، عملیات مشتری و تسویه‌های مجاز؛ بدون اختیار تغییر موجودی، اطلاعات پایه کالا، تأمین‌کننده/خرید یا مدیریت کاربران.
- فقط‌مشاهده: دسترسی خواندنی به صفحات عملیاتی مجاز؛ بدون امکان ثبت یا تغییر عملیات و بدون دسترسی به پشتیبان کامل، گزارش ممیزی و فهرست کاربران.

کنترل دسترسی در API سمت سرور اعمال می‌شود و صرفاً مخفی‌کردن دکمه‌ها در رابط کاربری مبنای امنیت نیست. تست یکپارچه ماتریس نقش‌ها باید دسترسی مثبت مدیر به مدیریت انبار و دسترسی منفی صندوقدار به عملیات مدیریتی را نیز پوشش دهد.

## گزارش‌های حسابداری با تاریخ مؤثر

- صورت سود و زیان از پارامترهای اختیاری `fromDate` و `toDate` با قالب `YYYY-MM-DD` پشتیبانی می‌کند؛ هر دو مرز شامل گزارش هستند.
- تراز آزمایشی و ترازنامه از `toDate` به‌عنوان تاریخ مبنای گزارش پشتیبانی می‌کنند و مانده حساب‌ها را تا پایان همان روز محاسبه می‌کنند.
- تاریخ نامعتبر، پارامتر تکراری/ناشناخته و بازه معکوس با پاسخ `400` رد می‌شود. بدون پارامتر، رفتار قبلی (کل سوابق) حفظ می‌شود.

## فیلتر تاریخ در رابط گزارش‌ها

- در صفحه حسابداری، بازه انتخابی روی صورت سود و زیان، فهرست تراکنش‌ها و دفتر روزنامه اعمال می‌شود؛ تراز آزمایشی در همان صفحه تا پایان تاریخ مقصد محاسبه می‌شود.
- در گزارش‌های مدیریتی، سود و زیان به بازه انتخاب‌شده و ترازنامه به تاریخ مقصد محدود می‌شود.
- خالی گذاشتن هر دو تاریخ، گزارش تمام‌دوره را نمایش می‌دهد. بازه معکوس پیش از ارسال درخواست رد می‌شود. خروجی CSV صفحه حسابداری شامل خلاصه سود و زیان، دفتر روزنامه و تراز آزمایشی با همان بازه انتخابی است؛ خروجی با UTF-8 BOM و خنثی‌سازی سلول‌های فرمول‌مانند تولید می‌شود. گزارش جریان نقدی نیز گردش هر سند صندوق و وجوه در راه کارت‌خوان/پرداخت آنلاین، جمع ورودی، خروجی و خالص تغییر وجه نقد را در همان بازه محاسبه می‌کند و در صفحه حسابداری و خروجی CSV نمایش می‌دهد. صفحه گزارش‌های مدیریتی نیز خروجی CSV شامل خلاصه مالی، فروش محصول و سفارش‌های همان بازه را ارائه می‌کند.
- فهرست سفارش‌ها و فروش به تفکیک محصول نیز با همان بازه تاریخ فیلتر می‌شوند؛ شمار مشتریان و موجودی انبار، وضعیت جاری را نشان می‌دهند و تاریخی نیستند.

## حفاظت از فایل‌های داخلی

سرور HTTP فقط دارایی‌های لازم مرورگر را از web root ارائه می‌کند. فایل‌های پایتون، مستندات، تست‌ها و قالب‌های استقرار و همچنین پوشه‌های `deploy` و `tests` از دسترسی استاتیک مسدود هستند؛ این محدودیت با تست یکپارچه رگرسیون کنترل می‌شود.

## API فعلی

- `GET /api/health` برای زنده‌بودن سرویس، `GET /api/ready` برای بررسی یکپارچگی SQLite، کلیدهای خارجی، جداول ضروری و تاریخچه migration، و `GET /api/setup-status`
- `POST /api/setup` برای ایجاد اولین کسب‌وکار و حساب مالک (رمز حداقل ۱۲ نویسه)
- `POST /api/login` و `POST /api/logout`
- `GET /api/me`، `POST /api/account/password` برای تغییر رمز حساب فعلی با تأیید رمز قبلی و ابطال نشست‌های قبلی، `GET/POST /api/users`، `DELETE /api/users/{id}`، `POST /api/users/{id}/password` برای بازنشانی رمز کاربران توسط مالک، `POST /api/users/{id}/role` برای تغییر نقش فعال به مدیر/صندوقدار/فقط‌مشاهده (فقط مالک؛ نشست‌های قبلی کاربر باطل و رویداد ممیزی ثبت می‌شود)، و `GET /api/audit-log` برای مشاهده تاریخچه ممیزی
- `GET /api/modules`، `GET /api/licenses/status` و `POST /api/licenses/activate`
- `GET/POST /api/orders`، `GET /api/orders/{id}` برای جزئیات رسید و `DELETE /api/orders/{id}` برای برگشت سفارش
- `GET/POST /api/product-addons`، `POST /api/product-addons/{id}` و `DELETE /api/product-addons/{id}` برای مدیریت افزودنی کالا
- `GET /api/public/menu` و `POST /api/public/orders` برای منوی عمومی و سفارش QR همراه با افزودنی‌ها
- `GET /api/reports/sales-by-product` و `GET /api/reports/best-selling-today` برای رتبه‌بندی کالاها بر اساس فروش خالص پس از تخصیص دقیق تخفیف فاکتور به ردیف‌ها؛ گزارش پرفروش روز تعداد فروش، مبلغ خالص و تعداد سفارش را بر اساس تاریخ محلی سرور نمایش می‌دهد
- `GET /api/backup` و `POST /api/backup/restore` برای پشتیبان کامل و بازیابی اتمیک همان فضای کاری; بازیابی داده‌های کسب‌وکار، کاربران موجود را از نظر نام کاربری، رمز عبور، نقش و فعال/غیرفعال بودن تغییر نمی‌دهد تا دسترسی فعلی مدیران و نشست‌ها ناخواسته از بین نرود
- `GET/POST /api/transactions` و `DELETE /api/transactions/{id}` (برگشت با سند معکوس)
- `GET/POST /api/products`، `GET/POST /api/customers`، `GET /api/customers/{id}/ledger` و `POST /api/customers/{id}/payments`، `GET /api/customers/{id}/loyalty` برای مانده و گردش امتیازهای باشگاه
- `GET /api/inventory` و `POST /api/inventory/movements`
- سفارش‌های کافه دارای چرخه آماده‌سازی مستقل از وضعیت پرداخت هستند: `queued → preparing → ready → served`. دکمه‌های صف آشپزخانه در صفحه کافه هر مرحله را با مجوز مالک/مدیر/صندوقدار تغییر می‌دهند؛ پرش از مرحله، تغییر سفارش لغوشده و دسترسی viewer رد می‌شود و هر انتقال در audit log ثبت می‌شود. سفارش‌های قدیمی پیش از مهاجرت به‌عنوان تحویل‌شده علامت می‌خورند تا صف تاریخی ناخواسته ساخته نشود.
- `GET/POST /api/suppliers`، `GET /api/suppliers/{id}/ledger` برای گردش حساب و مانده بدهی تأمین‌کننده، `GET/POST /api/purchase-invoices` و `POST /api/purchase-invoices/{id}/payments` برای خرید، ورود موجودی، بدهی تأمین‌کننده و پرداخت جزئی/کامل
- نسخه ۴ پشتیبان علاوه بر داده‌های نسخه ۳، شناسه ترتیبی اسناد دفتر روزنامه را نیز حفظ می‌کند تا مرز دقیق محاسبه گردش نقدی شیفت‌های باز پس از بازیابی تغییر نکند؛ نسخه ۳ قدیمی با مرز زمانی سازگار بازیابی می‌شود.
- `GET /api/cash-register/shifts` وضعیت شیفت فعال، موجودی مورد انتظار و تاریخچه ۱۰۰ شیفت اخیر را برمی‌گرداند؛ `POST /api/cash-register/shifts/open` با موجودی اولیه و یادداشت، یک شیفت فعال برای هر فضای کاری افتتاح می‌کند و وجود شیفت فعال دوم را رد می‌کند؛ `POST /api/cash-register/shifts/{id}/close` فقط توسط افتتاح‌کننده یا مالک/مدیر مجاز است، وجه شمارش‌شده را با گردش خالص حساب نقدی ۱۰۰۰ در دفتر کل تطبیق می‌دهد و مغایرت را در گزارش و audit log نگهداری می‌کند. مالک، مدیر یا صندوقدار مجاز به افتتاح هستند. محاسبه از اسناد واقعی همه ماژول‌ها استفاده می‌کند، نه فقط سفارش‌های کافه؛ شیفت‌ها و مغایرت‌های بسته‌شده در پشتیبان نسخه ۴ نگهداری می‌شوند؛ نسخه ۴ شناسه ردیف‌های دفتر کل را نیز حفظ می‌کند تا موجودی شیفت باز پس از بازیابی دقیق بماند.
- `GET/POST /api/accounting/accounts`
- `GET /api/accounting/periods` فهرست دوره‌های بسته‌شده را نشان می‌دهد؛ `POST /api/accounting/periods/close` فقط برای مالک کسب‌وکار فعال است، تاریخ‌های معتبر تا امروز را می‌پذیرد، بازه‌های هم‌پوشان را رد می‌کند و رویداد را در audit log ثبت می‌کند. بستن دوره فقط پس از کنترل توازن تمام اسناد بازه انجام می‌شود؛ وجود سند نامتوازن باعث رد درخواست خواهد شد. بستن دوره برگشت‌ناپذیر است؛ همه مسیرهای ثبت سند (تراکنش، خرید/فروش انبار، دریافت/پرداخت و برگشت تراکنش) تاریخ سند را با دوره‌های بسته‌شده تطبیق می‌دهند و هر ثبت یا برگشت در بازه قفل‌شده را رد می‌کنند. دوره‌های بسته‌شده و تاریخچه شیفت صندوق همراه پشتیبان JSON فضای کاری نسخه ۴ صادر و بازیابی می‌شوند؛ نسخه ۱ قدیمی دوره مالی و شیفت صندوق را نداشت و در بازیابی قفل‌ها/شیفت‌های فعلی حفظ می‌شوند؛ نسخه ۲ دوره‌های مالی را دارد اما شیفت صندوق را ندارد، بنابراین تاریخچه شیفت فعلی حذف نمی‌شود؛ برای بازیابی نسخه ۱ یا ۲ وجود شیفت فعال مجاز نیست و ابتدا باید آن را ببندید تا مرز محاسبه وجه نقد از بین نرود.
 برای مشاهده و تعریف سرفصل سفارشی (فقط مالک/مدیر؛ کد یکتا در فضای کاری و ماهیت حساب غیرقابل‌تحمیل از سمت کلاینت). سرفصل‌های سیستمی موردنیاز عملیات خودکار مالی حتی پیش از اولین ثبت سند قابل غیرفعال‌سازی نیستند؛ سرفصل سفارشی فقط در صورت نداشتن سابقه ثبت قابل غیرفعال‌سازی است؛ `GET /api/accounting/account-ledger?accountId=...&fromDate=YYYY-MM-DD&toDate=YYYY-MM-DD&limit=200&offset=0` دفتر معین هر سرفصل را با مانده افتتاحیه، گردش کامل بدهکار/بستانکار دوره، مانده جاری هر ردیف و مانده اختتامیه ارائه می‌کند؛ صفحه‌بندی با اندازه پیش‌فرض ۲۰۰ و سقف ۵۰۰ ردیف، ترتیب جدیدترین ابتدا، `totalItems`، `hasMore` و `nextOffset` انجام می‌شود؛ مانده جاری بین صفحه‌ها پیوسته و مجموع گردش‌ها مستقل از صفحه‌بندی محاسبه می‌شود؛ خروجی CSV تمام صفحه‌ها را دریافت می‌کند؛ `GET /api/accounting/trial-balance`، `GET /api/accounting/balance-sheet`، `GET /api/accounting/profit-loss` و `GET /api/accounting/cash-flow` (گزارش جریان نقدی تاریخ‌دار)
- `GET/POST /api/gamenet/devices`، `POST/DELETE /api/gamenet/devices/{id}`، `GET /api/gamenet/sessions`، `POST /api/gamenet/sessions/{id}/adjust` برای انتقال نشست/تغییر تعداد بازیکن و حالت رایگان یا پولی با ثبت تاریخچه تعرفه، `GET /api/gamenet/sessions/{id}/segments` برای ریزبخش‌های صورتحساب و `POST /api/gamenet/sessions/{id}/end` برای تسویه تجمیعی با روش نقدی، کارت‌خوان، آنلاین یا اعتباری. هزینه هر بخش بر اساس دقیقه گرد می‌شود و مجموع بخش‌ها در پایان نشست تسویه می‌شود.
- `GET/POST /api/gamenet/reservations` و `POST /api/gamenet/reservations/{id}/cancel` برای رزرو دستگاه و جلوگیری از تداخل زمان‌ها؛ زمان‌های ورودی باید ISO-8601 همراه منطقه زمانی/اختلاف UTC باشند و لغو رزرو در retry تکراری امن است

توکن نشست به‌صورت hash در SQLite نگهداری می‌شود؛ نشست‌ها دارای مهلت بیکاری ۳۰ دقیقه‌ای با تمدید در درخواست معتبر و سقف عمر مطلق ۷ روز هستند. رمز عبور با PBKDF2-HMAC-SHA256 و salt تصادفی ذخیره می‌شود. ورود علاوه بر محدودیت هر نام کاربری، محدودیت تجمیعی هر IP نیز دارد؛ سفارش عمومی نیز rate-limit پایه دارد. تغییر رمز شخصی با تأیید رمز قبلی انجام می‌شود و نشست‌های قبلی باطل می‌شوند؛ بازنشانی رمز کاربران فقط در اختیار مالک است و مدیر نمی‌تواند رمز مالک را تغییر دهد. داده‌ها در API به tenant محدود هستند و تغییرات مهم در audit log ثبت می‌شوند. این API هنوز به بازبینی امنیتی مستقل، TLS و آزمون نفوذ پیش از انتشار عمومی نیاز دارد؛ مدیریت پایه کاربران (ایجاد، غیرفعال‌سازی، بازنشانی رمز و تغییر نقش‌های مالک/مدیر/صندوقدار/فقط‌مشاهده) پیاده‌سازی شده، اما سیاست مجوزهای ریزدانه و قابل‌تنظیم برای هر عملیات همچنان در نقشه راه است. برای دسترسی از شبکه عمومی، سرور را مستقیم بدون HTTPS و تنظیمات امنیتی در معرض اینترنت قرار ندهید.

## قابلیت‌های پیاده‌سازی‌شده فعلی

- داشبورد واکنش‌گرا با رابط فارسی و راست‌چین.
- ناوبری اولیه ماژول‌های کافه، گیم‌نت، حسابداری، مشتریان، انبار، گزارش‌ها و تنظیمات.
- ثبت، مشاهده و برگشت تراکنش‌های پایه درآمد و هزینه.
- جست‌وجوی تراکنش‌ها و محاسبه مجموع درآمد، هزینه و مانده.
- اعتبارسنجی مشترک تراکنش‌ها در `core.js`؛ مبلغ صحیح و مثبت، نوع، شناسه، تاریخ و محدودیت طول داده‌ها بررسی می‌شوند.
- خروجی پشتیبان JSON و بازیابی پشتیبان با اعتبارسنجی ساختار، نسخه، تعداد رکوردها و شناسه‌های تکراری.
- نگهداری موقت برخی داده‌های رابط در مرورگر؛ در قطع ارتباط با سرور، رابط فقط پیام وضعیت آفلاین نشان می‌دهد و عملیات نوشتن را متوقف می‌کند تا داده‌های جداگانه و همگام‌نشده ایجاد نشوند.
- سرور API مبتنی بر Python و SQLite، ایجاد فضای کاری/مالک، ورود با نشست bearer، محدودسازی تلاش ورود، ثبت/خواندن/برگشت تراکنش و audit log.
- دفتر حساب‌ها پایه با امکان تعریف سرفصل سفارشی توسط مالک/مدیر (کد ۴ تا ۱۲ رقم (با پشتیبانی از ارقام فارسی/عربی و لاتین)، نام و نوع حساب؛ ماهیت بدهکار/بستانکار به‌صورت قطعی از نوع حساب تعیین می‌شود)، ثبت رویداد ممیزی برای ایجاد سرفصل، ثبت خودکار سند دوبل برای درآمد/هزینه و سند معکوس به‌جای حذف سند مالی.
- کاتالوگ کالا، پرونده مشتری، دفتر بدهکار/بستانکار مشتری با مشاهده گردش کامل حساب، دریافت جزئی از بدهی، گردش انبار، محاسبه موجودی و جلوگیری از موجودی منفی.
- مدیریت تأمین‌کنندگان، گردش حساب و مانده بدهی، فاکتور خرید چندقلمی، ورود اتمیک کالا به انبار، تخصیص متناسب تخفیف فاکتور با توزیع دقیق باقیمانده ریالی و ثبت بهای خرید خالص، ایجاد بدهی در دفتر کل و پرداخت جزئی/کامل تأمین‌کننده.
- گزارش سود و زیان، تراز آزمایشی و ترازنامه پایه بر مبنای دفتر کل؛ معادله دارایی = بدهی + حقوق مالکانه بررسی می‌شود.
- باشگاه مشتریان: برنامه امتیازدهی قابل فعال/غیرفعال‌سازی و قابل تنظیم توسط مالک/مدیر، دفتر امتیاز تغییرناپذیر و tenant-scoped، امتیازدهی idempotent بر مبنای مبلغ خالص سفارش‌های نقدی/کارت‌خوان/آنلاین و برگشت خودکار امتیاز هنگام برگشت سفارش؛ فروش اعتباری تا تسویه امتیاز نمی‌گیرد.
- کافه POS: سبد سفارش، تخفیف فاکتور با تخصیص متناسب و دقیق به ردیف کالاها (بدون خطای گردکردن)، انتخاب مشتری و روش پرداخت؛ افزودنی‌های قابل تعریف برای هر کالا با قیمت مستقل، انتخاب چند افزودنی در هر ردیف سفارش، محاسبه قیمت نهایی و نگهداری snapshot نام/قیمت افزودنی در تاریخچه. ثبت سفارش اتمیک، کسر موجودی فقط برای کالای اصلی و ثبت درآمد/بهای تمام‌شده.
- سفارش QR عمومی: نمایش افزودنی‌های فعال هر کالا، انتخاب افزودنی توسط مشتری، محاسبه قیمت در سمت سرور و کنترل تکرار امن بر اساس محتوای سفارش.
- جزئیات سفارش و رسید چاپی شامل اقلام، افزودنی‌ها، تخفیف، روش پرداخت و مبلغ نهایی؛ قالب چاپ رول حرارتی ۵۸ میلی‌متری نیز فراهم شده است. شناسه پایدار و کنترل تکرار برای سفارش، فاکتور خرید، دریافت/پرداخت، گردش انبار و شروع نشست/رزرو گیم‌نت در تلاش مجدد شبکه استفاده می‌شود تا عملیات مالی و موجودی دوباره ثبت نشوند.
- منوی عمومی QR در `/order.html`، ثبت سفارش مهمان با شماره تماس، محدودیت نرخ درخواست، ایجاد پرونده مشتری و ثبت فروش اعتباری/مانده مشتری.
- گیم‌نت پایه: مدیریت دستگاه، نشست زمان‌دار، تعرفه ساعتی، حالت رایگان/پولی، رزرو بازه‌ای دستگاه با جلوگیری از هم‌پوشانی و اتصال رزرو به مشتری؛ هنگام شروع نشست، رزرو فعال فقط برای مشتری رزروشده قابل استفاده است.

- پوسته PWA و cache فایل‌های اصلی برای بارگذاری آفلاین.
- بررسی ساختار HTML و ارجاعات DOM، تست‌های واحد JavaScript، تست‌های یکپارچه API/SQLite و آزمون مرورگر Playwright برای راه‌اندازی، ورود، ناوبری حسابداری، ایجاد سرفصل سفارشی، ثبت تراکنش، ورود موجودی و سفارش POS کافه در گردش کیفیت GitHub Actions.

## لایسنس و ماژول‌ها

در اولین راه‌اندازی یک دوره آزمایشی ۱۴ روزه برای ماژول‌ها فعال می‌شود. کد لایسنس امضاشده، ماژول‌های مجاز و تاریخ انقضا را تعیین می‌کند و API نیز دسترسی ماژول‌ها را در سمت سرور بررسی می‌کند.

برای صدور کد، یک کلید محرمانه حداقل ۳۲ نویسه‌ای را فقط در محیط امن صادرکننده و سرور تنظیم کنید:

```sh
export MG_LICENSE_SECRET='یک-کلید-تصادفی-طولانی-و-محرمانه'
python license_tool.py --modules cafe,gamenet,accounting,customers,inventory,reports --days 365 --plan professional
python server.py
```

کلید صادرکننده باید هنگام اجرای سرور نیز تنظیم باشد و نباید داخل مخزن عمومی یا در اختیار مشتری قرار گیرد. کد خروجی را مالک کسب‌وکار در بخش تنظیمات وارد می‌کند. ابزار صدور کد باید فقط در محیط مورد اعتماد اجرا شود.

## بررسی پیش‌نیازهای استقرار

پیش از راه‌اندازی سرویس، تنظیمات محیط را بررسی کنید:

```sh
python deployment_preflight.py
```

برای کنترل سخت‌گیرانه‌تر پیش از استقرار عملیاتی، متغیرهای `MG_ENV=production`، `MG_LICENSE_SECRET` (حداقل ۳۲ نویسه) و `MG_PUBLIC_URL` با نشانی HTTPS معتبر را تنظیم و سپس اجرا کنید:

```sh
MG_ENV=production python deployment_preflight.py --production
```

این ابزار پیکربندی bind، پورت، مسیر پایگاه داده و پشتیبان خارج از web root و سیاست نگهداری پشتیبان را بررسی می‌کند. مقدار `MG_HOST` باید IP صریح یا `localhost` باشد؛ bind با نام میزبان DNS رد می‌شود تا مقصد اتصال با تغییر DNS مبهم یا ناخواسته نشود. این بررسی جایگزین TLS واقعی، reverse proxy، فایروال، ممیزی امنیتی یا آزمون نفوذ نیست.

## استقرار عملیاتی با Nginx و systemd

نمونه‌های آماده در پوشه `deploy/` قرار دارند:

- `deploy/systemd/mg-business.service`: سرویس systemd با کاربر اختصاصی، محدودیت دسترسی فایل‌سیستم و مسیرهای نوشتنی مشخص.
- `deploy/systemd/mg-business.env.example`: الگوی تنظیمات production؛ کلید لایسنس را با مقدار تصادفی امن جایگزین کنید و فایل نهایی را فقط در اختیار root و کاربر سرویس قرار دهید.
- `deploy/nginx/mg-business.conf.example`: reverse proxy با TLS؛ دامنه و مسیر گواهی را جایگزین کنید.

نمونه مسیر نصب روی Linux:

1. برنامه را در `/opt/mg-business` قرار دهید و کاربر سیستمی `mg-business` بسازید.
2. مسیرهای `/var/lib/mg-business` و `/var/backups/mg-business` را بسازید و مالکیت آن‌ها را به کاربر سرویس بدهید.
3. فایل محیط را در `/etc/mg-business/mg-business.env` قرار دهید، مجوز آن را `0600` کنید و `MG_LICENSE_SECRET` را با یک راز تصادفی حداقل ۳۲ نویسه‌ای جایگزین کنید.
4. `MG_PUBLIC_URL` را با دامنه HTTPS واقعی تنظیم کنید. وقتی Nginx روی همان میزبان است، `MG_TRUSTED_PROXIES=127.0.0.1/32,::1/128` را نگه دارید؛ Nginx باید `X-Real-IP` را با `$remote_addr` بازنویسی کند.
5. قبل از فعال‌سازی سرویس، `deployment_preflight.py --production` را با همان متغیرهای محیطی اجرا کنید.
6. فایل systemd را در `/etc/systemd/system/` نصب و سرویس را فعال کنید؛ سپس پیکربندی Nginx را فعال و `nginx -t` را اجرا کنید.

Backend باید فقط روی `127.0.0.1:8080` گوش دهد. پورت ۸۰/۴۴۳ را در فایروال برای Nginx باز کنید و پورت ۸۰۸۰ را عمومی نکنید. فقط IP/CIDR مربوط به reverse proxy واقعی را در `MG_TRUSTED_PROXIES` وارد کنید؛ اعتماد به هدرهای forwarding از کلاینت‌های عمومی ناامن است.

این نمونه‌ها برای Linux با systemd و Nginx هستند؛ نصب واقعی همچنان نیازمند صدور گواهی TLS معتبر، تنظیم DNS، فایروال، مدیریت امن رازها و آزمون بازیابی پشتیبان است.

## وضعیت آمادگی و محدودیت‌ها

**این مخزن هنوز محصول آماده بهره‌برداری تجاری نیست.** داشبورد و تراکنش‌های محلی قابلیت‌های پایه‌اند و وجود آن‌ها به معنی پیاده‌سازی ماژول‌های عملیاتی نیست.

موارد زیر هنوز پیاده‌سازی نشده‌اند و برای انتشار واقعی ضروری‌اند:

- API فعلی برای استقرار محلی تک‌فروشگاهی است؛ زیرساخت چندشعبه‌ای/چندمستاجری کامل، استقرار مرکزی و مدیریت عملیاتی پایگاه داده هنوز تکمیل نشده است.
- مدیریت کامل کاربران و نقش‌ها، بازیابی رمز، سیاست‌های نشست پیشرفته و مجوزهای ریزدانه؛ احراز هویت پایه و جداسازی داده tenant در API موجود است.
- حسابداری کامل شامل بستن دوره، مالیات، مغایرت‌گیری بانک، خزانه‌داری و گزارش‌های قانونی هنوز باقی است؛ دفتر دوبل، تراز آزمایشی، ترازنامه پایه، ایجاد سرفصل سفارشی و غیرفعال‌سازی ایمن سرفصل استفاده‌نشده (با جلوگیری از حذف حساب دارای سابقه سند) پیاده شده‌اند.
- تکمیل کافه شامل میزها، منوی قابل تنظیم، صف آشپزخانه و گردش آماده‌سازی، مدیریت چند صندوق/ترمینال مستقل و اتصال عملیاتی کارت‌خوان و گزارش‌های کامل هنوز باقی است؛ POS پایه، سفارش QR، افزودنی‌ها، رسید ۵۸ میلی‌متری، برگشت سفارش و تخصیص دقیق تخفیف به ردیف کالاها پیاده شده‌اند.
- توسعه کامل گیم‌نت شامل سانس‌های دوره‌ای، تعرفه‌های زمان‌بندی‌شده/چندسطحی، چندنفره پیشرفته، شارژ کیف پول و گزارش‌های تخصصی هنوز باقی است؛ مدیریت دستگاه، رزرو بازه‌ای، انتقال نشست، تغییر تعداد بازیکن و حالت رایگان/پولی با تاریخچه تعرفه، محاسبه بخش‌بندی‌شده و تسویه نقدی/کارت‌خوان/آنلاین/اعتباری پیاده شده‌اند.
- CRM پیشرفته شامل تقسیم‌بندی مشتریان، کمپین‌ها، کوپن‌ها، قوانین سطح/انقضای امتیاز و بازخرید امتیاز هنوز باقی است؛ پرونده و گردش حساب مشتری، دریافت بدهی و باشگاه امتیازدهی قابل تنظیم با دفتر تغییرناپذیر، امتیازدهی تکرارنشدنی و برگشت خودکار امتیاز سفارش پیاده شده‌اند.
- فاکتور خرید چندقلمی و تخصیص دقیق تخفیف خرید پیاده شده‌اند؛ فاکتور برگشت خرید، انبارگردانی دوره‌ای، انتقال بین انبارها، سریال/بچ و سیاست‌های پیشرفته ارزش‌گذاری موجودی باقی‌اند.
- زیرساخت کامل چندشعبه‌ای/چنددستگاهی، همگام‌سازی تراکنشی آفلاین، ثبت دستگاه مورداعتماد، اجاره/فنسینگ رهبر، حل تعارض و failover ایمن هنوز پیاده‌سازی نشده است؛ PWA فقط پوسته رابط را cache می‌کند و در قطع سرور عملیات مالی/عملیاتی را متوقف می‌کند.
- پشتیبان‌گیری زمان‌بندی‌شده محلی/سروری، نسخه‌برداری JSON و بازیابی اعتبارسنجی‌شده پیاده شده‌اند؛ مانیتورینگ مرکزی، هشدار مستقل، رمزنگاری پشتیبان در حالت سکون، آزمون بازیابی در مقیاس عملیاتی و runbook رخداد باقی‌اند.
- بازبینی امنیتی مستقل، تست نفوذ، تست مرورگر end-to-end، آزمون بار و پایداری طولانی‌مدت، و اعتبارسنجی نصب/ارتقا روی محیط واقعی پیش از انتشار عمومی ضروری‌اند.

## اصول معماری هدف

- رابط PWA واکنش‌گرا با پشتیبانی فارسی/انگلیسی و RTL/LTR.
- API و لایه دامنه مستقل از رابط کاربری.
- SQLite برای استقرار تک‌فروشگاهی اولیه و امکان مهاجرت به پایگاه داده سروری در استقرار چندکاربره.
- هر عملیات مالی در تراکنش پایگاه داده انجام شود و اسناد حسابداری تغییرناپذیر و قابل ممیزی باشند.
- هر رکورد تجاری به فضای کاری/کسب‌وکار مربوط باشد و مجوزها در سمت سرور اعمال شوند.
