# MG Business Web

پلتفرم وب مستقل MG Business برای مدیریت یکپارچه فروش، انبار، مشتریان، حسابداری، کافه/رستوران و گیم‌نت.

## وضعیت فعلی توسعه
- رابط React + Vite فارسی و RTL: پیش‌نمایش رابط کاربری است و هنوز به API متصل نشده است.
- Backend با ASP.NET Core 10 و تفکیک Domain / Infrastructure / API.
- احراز هویت Identity API، توکن bearer، محدودیت تلاش ورود و rate limit.
- ساخت کسب‌وکار، شعبه و عضویت کاربران با نقش‌های مختلف.
- انتخاب tenant و branch در سرور اعتبارسنجی می‌شود؛ شناسه ارسالی کلاینت به‌تنهایی مجوز نیست.
- APIهای پایه مشتریان، کالا/انبار، اسناد حسابداری دوبل، فروش، پرداخت، آشپزخانه کافه و تایمر گیم‌نت ایجاد شده‌اند.
- تست‌های دامنه و یکپارچه SQLite و CI برای Backend اضافه شده‌اند.
- SQLite برای توسعه/آزمایش و PostgreSQL برای استقرار مرکزی پشتیبانی می‌شود.

این پروژه هنوز نسخه عملیاتی یا آماده استفاده تجاری نیست. مهاجرت اولیه EF Core برای PostgreSQL و model snapshot در مخزن ثبت شده‌اند؛ اجرای migration در زمان شروع API فقط با تنظیم صریح فعال می‌شود. برای استقرار SQLite هنوز migration جداگانه لازم است. مجوزدهی ماژولار، خرید/تأمین‌کننده، مالیات، حساب تفصیلی مشتری، سفارش آنلاین، رزرو، باشگاه مشتریان، همگام‌سازی آفلاین و اتصال کامل رابط وب هنوز تکمیل نشده‌اند.

## اجرای رابط وب
```bash
npm install
npm run dev
```

ساخت production:
```bash
npm run build
```

## اجرای API
نیازمند .NET 10 SDK:
```bash
dotnet run --project backend/src/MG.Business.Api/MG.Business.Api.csproj
```

مستندات API و محدودیت‌های استقرار در [backend/README.md](backend/README.md) و اصول معماری در [docs/architecture/FOUNDATION.md](docs/architecture/FOUNDATION.md) قرار دارند.

## انتشار آزمایشی
GitHub Pages فقط فایل‌های استاتیک frontend را میزبانی می‌کند؛ API و پایگاه داده باید روی زیرساخت جداگانه اجرا شوند. انتشار عمومی پس از merge شدن تغییرات و فعال‌سازی Pages روی شاخه اصلی انجام می‌شود؛ در حال حاضر این پروژه هنوز نسخه منتشرشده عملیاتی ندارد.

## اصول غیرقابل مذاکره
- اطلاعات هر کسب‌وکار باید به‌صورت امن از سایر کسب‌وکارها جدا باشد.
- داده‌های مالی و موجودی باید دارای تاریخچه و قابلیت حسابرسی باشند.
- ثبت فروش، پرداخت، گردش موجودی و سند مالی باید در یک تراکنش سازگار انجام شود.
- قابلیت‌های آفلاین باید صف عملیات پایدار و همگام‌سازی قابل تکرار داشته باشند.
- هیچ قابلیت نمایشی یا mock نباید به‌عنوان قابلیت عملیاتی معرفی شود.
- قبل از استفاده از داده واقعی، migration، پشتیبان‌گیری، امنیت و تست استقرار باید تکمیل شوند.
