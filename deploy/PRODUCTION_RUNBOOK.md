# Production deployment and operations runbook

This runbook deploys MG Business Web on a Debian/Ubuntu Linux host behind Nginx. The application server remains bound to loopback; only Nginx is exposed to the internet.

## 1. Prerequisites

- A supported Debian/Ubuntu server with a fixed public IP.
- A domain whose DNS A/AAAA records point to that server.
- Inbound TCP 80 and 443. Do not expose TCP 8080.
- A dedicated, backed-up location for encrypted backups.
- A separately stored copy of the backup encryption key.

Install the operating-system packages:

```sh
sudo apt update
sudo apt install -y git python3 python3-cryptography nginx certbot
```

## 2. Create the service account and directories

```sh
sudo useradd --system --home /var/lib/mg-business --shell /usr/sbin/nologin mg-business
sudo install -d -o root -g mg-business -m 0750 /opt/mg-business
sudo install -d -o mg-business -g mg-business -m 0750 /var/lib/mg-business
sudo install -d -o mg-business -g mg-business -m 0750 /var/backups/mg-business
sudo install -d -o root -g root -m 0750 /etc/mg-business
sudo git clone https://github.com/Mahdi0383/MG-Business-Web.git /opt/mg-business
sudo chown -R root:mg-business /opt/mg-business
sudo find /opt/mg-business -type d -exec chmod 0750 {} \;
sudo find /opt/mg-business -type f -exec chmod 0640 {} \;
```

The application process must be able to read the release files but must not be able to modify its own code.

## 3. Configure secrets and production environment

Generate a unique license-signing secret and an independent 32-byte backup key:

```sh
openssl rand -hex 32
cd /opt/mg-business
sudo -u mg-business /usr/bin/python3 backup_manager.py --generate-key
```

Copy the environment template and replace every placeholder, including the actual domain:

```sh
sudo cp /opt/mg-business/deploy/systemd/mg-business.env.example /etc/mg-business/mg-business.env
sudoedit /etc/mg-business/mg-business.env
sudo chown root:root /etc/mg-business/mg-business.env
sudo chmod 0600 /etc/mg-business/mg-business.env
```

Required production values:

- `MG_ENV=production`
- `MG_HOST=127.0.0.1` and `MG_PORT=8080`
- `MG_PUBLIC_URL=https://your-real-domain`
- `MG_TRUSTED_PROXIES=127.0.0.1/32,::1/128` when Nginx is local
- `MG_MAX_HTTP_WORKERS=64` to cap concurrent application requests (valid range: 4–512)
- `MG_REQUEST_TIMEOUT_SECONDS=15` to close slow/stalled client requests (valid range: 5–120)
- A unique `MG_LICENSE_SECRET` of at least 32 characters
- A valid `MG_BACKUP_ENCRYPTION_KEY` generated by `backup_manager.py`
- `MG_DATA_DIR`, `MG_DB_PATH`, and `MG_BACKUP_DIR` pointing to the dedicated directories above

Never commit secrets, put the backup key in the backup directory, or store the only copy of the key on the application server. Losing the key makes encrypted backups unrecoverable.

## 4. Obtain TLS certificates and configure Nginx

First ensure DNS resolves to this host and TCP 80 is reachable. Obtain the certificate:

```sh
sudo certbot certonly --standalone -d your-real-domain
```

Copy the example Nginx configuration, replace every occurrence of `business.example.com`, enable it, and validate:

```sh
sudo cp /opt/mg-business/deploy/nginx/mg-business.conf.example /etc/nginx/sites-available/mg-business
sudoedit /etc/nginx/sites-available/mg-business
sudo ln -s /etc/nginx/sites-available/mg-business /etc/nginx/sites-enabled/mg-business
sudo nginx -t
sudo systemctl reload nginx
```

Keep the backend bound to loopback. Configure the host firewall to allow only SSH administration and TCP 80/443; never add port 8080 to public firewall rules. Confirm automatic certificate renewal is enabled:

```sh
sudo certbot renew --dry-run
```

## 5. Install and start the systemd service

```sh
sudo cp /opt/mg-business/deploy/systemd/mg-business.service /etc/systemd/system/mg-business.service
sudo systemctl daemon-reload
sudo systemctl enable --now mg-business
sudo systemctl status mg-business --no-pager
```

The service startup script runs `deployment_preflight.py --production` before starting the server. A failed preflight must be fixed; do not bypass it.

Verify local health/readiness and public HTTPS:

```sh
curl --fail http://127.0.0.1:8080/api/health
curl --fail http://127.0.0.1:8080/api/ready
curl --fail https://your-real-domain/api/health
```

Inspect service logs:

```sh
sudo journalctl -u mg-business -n 200 --no-pager
sudo journalctl -u mg-business -f
```

Complete first-run setup in the browser. Create the owner account with a unique strong password, then activate the intended module license.

## 6. Backup verification and restore drill

Production backups are encrypted with AES-256-GCM. Schedule and retention are configured by `MG_BACKUP_INTERVAL_HOURS` and `MG_BACKUP_RETENTION`. Monitor free disk space and backup timestamps; a successful HTTP health check does not prove a recent backup exists.

List backup files and verify a selected snapshot without replacing the live database:

```sh
sudo -u mg-business ls -lh /var/backups/mg-business
sudo -u mg-business /usr/bin/python3 /opt/mg-business/backup_manager.py --verify /var/backups/mg-business/FILE.sqlite3.enc
```

Perform restore drills on a separate staging host using a copy of the encrypted backup and the separately escrowed key. Never experiment with restore commands against the only production database. For an approved production restore:

1. Announce downtime and stop the service.
2. Copy the current database and backup directory to a separate protected location.
3. Set `MG_BACKUP_ENCRYPTION_KEY` in the root shell environment.
4. Run the restore tool against the chosen verified snapshot.
5. Start the service and verify `/api/ready`, owner login, orders, balances, and active/closed operational records.
6. Record the restore duration and observed recovery point.

## 7. Safe upgrade procedure

1. Review the release notes and identify the exact target commit.
2. Verify that the latest encrypted backup exists and passes `backup_manager.py --verify`.
3. Stop the service and make an additional filesystem/database safety copy.
4. Fetch the release and fast-forward only; do not deploy an unreviewed working tree.
5. Run Python compilation, project smoke checks, backend tests, and browser E2E in CI before deployment.
6. Start the service; startup applies database migrations. Check `/api/ready` and inspect logs.
7. Run a small owner-approved transaction and verify the corresponding ledger/report before reopening normal operations.

Do not roll application code back across a database migration unless the matching database restore plan has been tested. Prefer a forward fix. If restoring a database is necessary, stop writes and follow the restore drill above.

## 8. Incident response checklist

- **Service unavailable:** inspect `systemctl status`, `journalctl`, disk space, and `/api/health`.
- **Not ready:** inspect `/api/ready` and migration/database integrity output; do not accept transactions until readiness returns.
- **TLS failure:** inspect certificate expiry and Nginx configuration; test renewal before restarting.
- **Backup failure:** inspect logs and free space, verify the encryption key is still available, and confirm the destination is writable by `mg-business`.
- **Suspected compromise:** restrict inbound traffic, preserve logs and backups, rotate owner credentials and exposed secrets, and obtain an independent security review before returning to public service.

## 9. Release gate

A green CI run and successful deployment preflight are necessary, not sufficient, for a commercial production launch. Before enabling public customer traffic, complete an independent security review and penetration test, verify restore drills and monitoring/alerting, test load and browser workflows on production-like infrastructure, and validate the actual payment-terminal/network setup.
